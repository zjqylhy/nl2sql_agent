# 阿里云 2 核 2GiB 容量验证

2026-10-11，验证源码版本 `09e552da954f6cfb72763a6a82e36b644ee4f9c9`。机器可读结果见 [测试数据](benchmarks/aliyun-2c2g-2026-10-11.json)。

## 结论

当前 API、Agent、Web 可以在 2 核、各服务合计 1.125GiB 的硬内存预算内运行，适合数据库外置的演示和小规模使用。首次上线可以从不超过 10 个同时查询的用户开始，根据真实 ECS、RDS 和模型响应时间调整。

50 用户规则查询突发测试通过；模型固定等待 15 秒时，50 用户的 P95 为 31.89 秒，未满足规格中的 30 秒目标。不能据此承诺完整的 50 活跃任务性能目标，也不能认定单纯增加内存即可解决排队问题。

## 测试条件与判定

- Docker Desktop Linux/amd64、cgroup v2。宿主有 32 个逻辑 CPU、约 15.18GiB 内存；没有将整个虚拟机缩小到 2GiB。
- API、Agent、Web 都限制到同一组逻辑 CPU `0,1`，三者实际只能共用这两个 CPU。保留云模板的独立 CPU 上限：1、1、0.5；上限相加不是额外分配 2.5 个 CPU。
- 内存硬上限分别为 512、512、128MiB，`memory_swap=memory`，禁用各应用容器的交换空间。只读根文件系统、`/tmp` tmpfs、非 root 镜像；真实运行镜像 ID 记录在测试数据中。[Docker 资源限制说明](https://docs.docker.com/engine/containers/resource_constraints/)
- 隔离的 MySQL 8.4 与 PostgreSQL 17 在应用预算之外，模拟外置数据库。测试数据库使用 tmpfs、局域容器网络，未模拟 RDS 磁盘性能、TLS 或跨网络延迟。
- 使用官方 Olist CSV，按现有导入器构建 99,441 条订单事实、日期索引与只读视图；分析基准为 2018-08-31。CSV 哈希已记录。
- 50 个独立测试用户和有效会话；每个用户同时最多一个任务。会话在测试数据库中预置，登录流程不属于本次负载。
- 10 类规则查询覆盖六个指标、1–3 个指标组合、月/日/州分组、联合维度、筛选和 Top N。先由独立 oracle 校验基准结果，再对并发结果的计划与数据逐项哈希比对。数据库为重复查询后的热缓存。
- 每轮所有用户同步提交；等待全批完成后进入下一批。延迟包含 POST、任务领取、执行和终态轮询，轮询间隔 200ms。P95 用最近秩计算，统计所有任务，不删除慢请求。
- 模型阶段使用独立 HTTPS 测试服务，固定等待 5 秒或 15 秒后返回正确意图，并验证真实 Agent 确实调用了模型接口。这是等待与资源测试，不是供应商性能、限流、Token 费用或模型准确率验收；未调用付费模型。
- 判定：完成且答案一致、无 OOM/异常重启，简单问数 P95 ≤30 秒。短时测试不代替持续稳定性或 99.9% 可用性验收。

## 结果

| 查询路径 | 同时提交用户 | 批次数 | 完成且答案一致 | P95 / 秒 | 最大 / 秒 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 规则 | 1 | 20 | 20/20 | 0.42 | 0.42 |
| 规则 | 5 | 10 | 50/50 | 1.24 | 1.42 |
| 规则 | 10 | 5 | 50/50 | 2.45 | 2.67 |
| 规则 | 20 | 3 | 60/60 | 4.92 | 5.13 |
| 规则 | 50 | 3 | 150/150 | 11.91 | 12.52 |
| 模拟模型等待 5 秒 | 10 | 2 | 20/20 | 7.56 | 7.58 |
| 模拟模型等待 5 秒 | 50 | 2 | 100/100 | 17.00 | 17.44 |
| 模拟模型等待 15 秒 | 10 | 2 | 20/20 | 17.53 | 17.61 |
| 模拟模型等待 15 秒 | 50 | 2 | 100/100 | **31.89，未达标** | 32.66 |

共 570 个计时任务全部完成且答案一致；另有 11 个基准查询。共记录 581 次执行、241 次模拟模型调用。SSE 终态读取与断点续传通过。较慢模型阶段额外只读采样，实际观察到 50 个任务处于 `querying`；这不代表 Agent 内部同时执行了 50 次调用。

| 应用 | 内存采样峰值 / MiB | CPU 采样峰值 |
| --- | ---: | ---: |
| API | 13.71 | 19.23% |
| Agent | 80.19 | 22.55% |
| Web | 9.62 | 8.51% |

同一采样帧内的应用内存合计最高为 **96.66MiB**，CPU 合计最高为 36.98%（单个逻辑 CPU 满载为 100%，两核容量为 200%）。各服务的峰值发生时间不同，不能把独立峰值当作同时峰值。Docker stats 内存是扣除部分缓存后的工作集，不等同于进程 RSS 或全机内存。

成功采样 120 帧，失败 9 次，阶段切换重建 Agent 时存在采样间隙，因此采样峰值不代表所有瞬时峰值。模型阶段 Agent 的 cgroup `memory.peak` 为 82.37MiB，`memory.events` 中 `max/oom/oom_kill` 均为 0；CPU 仅限流 3 次，共约 17.61ms。结束时三个应用均健康、重启次数为 0、`OOMKilled=false`。测试容器与临时数据库已清理。

## 瓶颈及部署边界

1. 当前 [Go Worker](../internal/api/worker.go) 每 250ms 只领取一个任务，测试规则吞吐约为 4 个任务/秒。持续到达率超过此速度会积累队列，50 用户突发完成不等于持续 50 用户无排队。
2. [Agent 查询入口](../agent/runtime/app.py) 是同步接口。实际镜像中 AnyIO 默认线程 limiter 为 40；模型 HTTP 调用也同步等待。50 用户、15 秒模型等待时会叠加领取延迟和线程等待，符合本次超过 30 秒的结果。进一步满足该目标需调整调度/执行并发方案，再按真实模型延迟验证。
3. 云模板应用硬内存上限合计 1,152MiB，2GiB 主机剩余 896MiB 需容纳 Linux、Docker、宿主 Nginx、日志采集等。发布期间额外迁移容器上限为 512MiB，若应用与迁移同时达到上限，宿主仅余 384MiB；本次没有验证升级时的全机峰值。不要在 2GiB ECS 上构建镜像或导入分析数据，使用已有 CI 与独立导入流程。
4. 本次结论不覆盖 MySQL、PostgreSQL 与应用都放在同一台 2c2g 主机，也不覆盖在 ECS 本地运行大模型。复杂归因、报告和任意 SQL 不属于当前受控问数测试范围。
5. 具体实例族仍影响 CPU 表现。阿里云共享型实例可能有性能波动；2 核参数不能保证与本机两核相同的处理速度。[阿里云共享型实例说明](https://help.aliyun.com/zh/ecs/user-guide/shared-instance-families)
6. 实际上线还应在目标 ECS 上接入真实 RDS、HTTPS、日志采集和模型，复跑典型查询与持续负载，检查全机可用内存、队列、供应商限流及升级过程。当前结果属于上线前容量证据，未在阿里云实例上完成验收。
