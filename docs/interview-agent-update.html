4.1 60 秒介绍逐字稿

我做的是面向推送与设备数据的 AI Agent 应用，重点是让模型的规划能力在可检查的边界内执行。用户从同一入口提问，明确条件取数由 AI 一次生成完整步骤，程序校验依赖后执行；“点击率为什么下降”这类开放问题，则让 AI 根据真实中间结果选择下一步。执行控制层负责权限、范围、预算、工具和证据：约定保存在服务端，模型不能自己改日期或编数字。大结果只给有省略说明的预览，需要时再读取；任务中断按回执恢复，失败由用户明确重试。当前数据为模拟数据，程序能核对计算与引用，不能因此证明业务因果或所有问题都分析正确。

4.2 详细介绍逐字稿

这个项目从用户的分析目标出发，而不是要求用户先选固定题型。统一入口同时识别意图和解析条件，不为分类额外增加一次模型请求。“近七天各厂商发送量、到达率如何变化”属于明确取数；“最近点击率下降，调查原因”需要依中间结果选择调查方向，进入开放分析。下降、上升、波动不是业务枚举；预先实现的是查询、比较、汇总、观察结果和比率拆解等基础能力。

明确取数采用一次规划、程序执行。AI 生成结果要求及 A→B→C 的完整步骤；程序先检查步骤依赖、输出字段、筛选来源和最终覆盖，再用完整结果绑定后续参数。开放分析采用逐轮决策：AI 看到已确认约定、真实结果预览、反馈和剩余额度，只提出一个动作；程序判断能否执行，保存完整产物，再让模型决定继续调查、申请扩大范围或提交报告。

执行控制层不是一段“请遵守规则”的提示，而是模型无法绕过的代码路径。它在调用前检查身份、数据版本、范围与预算，在执行时使用白名单视图和参数化只读 SQL，在交付时重新解析引用、计算业务数字并检查已回答事项。用户范围与实际权限分开：约定是本次边界，实际权限每次重新检查；扩大范围必须展示具体变更并等待确认。

架构使用 Python、FastAPI、LangGraph、PostgreSQL 和 React。API 接纳和读取持久任务，独立 Worker 执行流程；检查点记录下一节点，操作账本记录调用与用量，业务任务和持久事件供页面展示。它是一个 Agent 的受控循环，没有为了展示复杂度而引入多 Agent。到达率、点击率和设备指标由程序维护统一口径，不把缺回执当失败，不平均各组比率，不混合设备与消息粒度。

真实接入暴露过几类问题：小探针成功却因月额度预留不足拒绝完整请求；有效约定少了一层包装被拒；两轮补充被固定协议挤出输入预算；模型回传程序生成字段造成约定误判；重复继承同一筛选导致比较被拒。每次按回执区分请求是否发送、SQL 是否执行、已有证据能否复用，再增加反例测试和部署验证。面试重点是解释这些取舍与边界，不把“使用了某框架”当成成果。

4.3 实现链路复习

统一输入 → AI 识别意图并解析必要条件 → 缺条件先补充
  明确取数 → 完整计划 → 执行前检查 → 按依赖执行与检查 → 最终覆盖核对
  开放分析 → 保存已确认约定 → 读取观测与预算 → AI 提一个动作
           → 程序检查并执行 → 保存完整证据 → 继续决策 / 申请变更 / 检查报告
任一步失败 → 保留回执与用量；不把未知调用自动重发，不把部分结果写成完整完成。

4.5 项目问答与追问演练：以 AI Agent 应用为主

4.5.1 N01｜这个项目解决什么问题？为什么需要 Agent？

我的回答：明确条件问题需要可靠地执行，开放问题需要根据结果改变调查方向，所以我保留两条执行方式。比如“按厂商列趋势”可一次规划执行，“点击率为何下降”要先核实前提，再决定查通道、厂商或模板。Agent 的价值是受约束的调查决策，而不是把 SQL 工具包一层聊天。

4.5.2 N02｜哪些是固定流程，哪些由模型决定？

我的回答：鉴权、预算、执行、计算、证据保存与报告检查是固定程序；开放任务的下一调查方向由模型决定。明确取数在开始时由模型规划，之后由代码闭环执行。是否多步与是否开放分析是两回事。追问时我会用 A 查候选、B 排名、C 查选中组举例，解释为什么它仍是明确取数。

4.5.3 N03｜统一入口怎样识别任务类型，条件不全怎么办？

我的回答：同一次初始解析返回任务类型及约定或完整计划，不单独调用一次分类模型。缺日期、应用范围、指标定义或回执窗口时追问，保留原问题和全部已提交补充。不用“变化”或“为什么”等关键词直接替代意图判断；表单可以不经过模型生成相同格式的明确计划。

4.5.4 N04｜任务约定是谁生成、怎样保存，权限也听模型的吗？

我的回答：AI 从自然语言生成 JSON 草案，程序校验后按版本保存在服务端。它包含目标、期间、筛选、观察口径和交付要求。程序生成可探索权限；已确认后模型优先只返回动作，不反复抄写约定。约定限定本次范围，不能扩大账号权限，执行时还要重新查实际授权。

4.5.5 N05｜AI 一次生成 A→B→C，程序怎样提前知道能不能跑？

我的回答：先检查操作是否存在、步骤编号是否重复、依赖是否有环、引用是否指向合法前序输出，再推导每步字段和粒度，检查 B 是否真的产出 C 所需的分组列。最后核对输出是否覆盖约定的指标、维度、期间和选组要求。合法计划也可能运行时无数据或超限，所以每步执行和最终交付还要检查。

4.5.6 N06｜静态校验能保证最终结果就是用户想要的吗？

我的回答：不能。它能证明结构、依赖和约定覆盖，不能证明 AI 把自然语言理解对了。因此要把关键口径显式化，保存原问题和补充，在评测中同时核对解析条件和实际结果。不能用“检查过 JSON”代替语义准确率，也不能把另一个模型的赞同当成计算证明。

4.5.7 N07｜开放分析每轮究竟发生什么？遇到没定义过的题型呢？

我的回答：每轮给模型约定、观测、反馈和剩余预算；模型提出一个已注册动作，程序检查后执行并记录结果，再回到决策。业务题型不枚举，模型可以组合已有基础能力回答新问题。数据或工具不存在时应说明缺口；“开放”不代表绕过目录去读任意表或凭空编造字段。

4.5.8 N08｜A 的结果会给模型吗？大结果怎么处理？

我的回答：会给足以决定下一步的真实摘要，包括结果编号、口径、整体值、行数和固定顺序预览；默认预览最多前三行，明确省略数量和规则。完整结果在服务端，模型可用检查工具读取有限页，单页最多二十行。当前单个查询结果仍有一千组和大小上限，超限不能伪装成完整结果。

4.5.9 N09｜工具调用怎样由代码把关？模型可以自己写 SQL 吗？

我的回答：当前新推送流程让模型提交结构化查询或动作，程序编译固定视图和绑定参数。注册工具检查字段、指标依赖、时间、范围、父分组真实性和当前授权；SQL 还经过只读语法检查、只读账号和超时限制。不能只靠提示要求“不要写危险 SQL”。数据库十秒、查询客户端十五秒等限制仍有效。

4.5.10 N10｜JSON 合法为何仍可能失败？

我的回答：结构格式只是第一层。约定可能缺口径，步骤可能引用不存在的列，工具可能拿不同范围证据比较。真实接入中模型曾直接返回合法约定而省略 contract 包装，我只兼容可识别的完整对象，仍执行同一套校验，不通过补造指标或放松范围把它强行跑通。

4.5.11 N11｜模型说完成、写出一个数字，程序就交付吗？

我的回答：不会。报告要列回答事项、证据引用、数值位置、假设、已查与未查方向；程序解析引用，检查任务、版本、权限、完整性和行号，再从产物取数。模型不能在解释里自填业务数字。程序能够核对这些可计算事实，但不能自动证明解释覆盖所有关键原因或业务因果成立。

4.5.12 N12｜比率下降如何解释？组内变化和结构变化是什么意思？

我的回答：整体比率是总分子除以总分母，不是组比率的平均。整体下降可能来自某组自身变差，也可能是低比率组占比增加。程序对同一互斥完整分组计算组内与结构贡献，并校验贡献之和等于整体差值。它解释统计分布，不证明某厂商故障或文案导致下降；不同维度的贡献不能叠加。

4.5.13 N13｜两个自然月天数不同，还能比较吗？

我的回答：开放分析中，用户已确认的不重叠期间可以比较相同筛选与观察口径下的比率，但要说明发送日期结构和季节性未被消除。计数和时延不能因此直接放宽；明确取数固定比较步骤仍要求等长。程序不能为了通过检查，把用户确认的日期偷偷改成另一组。

4.5.14 N14｜观察窗口、发送期间和设备时点有何区别？

我的回答：发送期间限定哪批消息，观察窗口限定发送后多长时间内的回执，设备时点决定查询哪个历史状态。发送结束加观察时长不能越过数据截止。缺回执保留未知，不等于未到达；点击/发送率与点击/到达率是不同指标，后者只统计已确认到达且点击的交集。

4.5.15 N15｜设备和发送数据怎样避免重复计数？

我的回答：先定义一行的业务粒度。一次逻辑投递可以有多次发送尝试和多条回执，重试不增加逻辑发送量；回执先归并再关联。设备状态历史先归并为互斥区间，活跃按应用设备去重。不能把设备、多个 Token、推送和前台事件直接联表后用 COUNT(*)。

4.5.16 N16｜还需要一次模型质量评审或人工审批吗？

我的回答：当前默认没有每次任务结束后再调用一个评审模型，也没有强制逐任务人工审核。程序完成检查负责可计算约束；解释是否充分、调查是否有价值，需要独立的质量评测或人工抽样判断。若未来引入模型评审，它也要单独记预算、记录依据，不能代替数字计算和权限检查。

4.5.17 N17｜预算怎样约束 Agent，和网关配额有何区别？

我的回答：任务保存冻结的模型、价格和调用配置，代码控制模型次数、工具次数、SQL、活跃时间、Token 与费用。调用前先预留，确定用量再结算；未知用量保留预留。网关月配额是另一层共享限制，即使任务还有预算也可能被网关拒绝。小探针成功不能证明完整请求的输入与输出预留也放得下。

4.5.18 N18｜失败能不能重试，如何防重复点击？

我的回答：先分清本地拒绝、明确失败和外部结果未知。用户点“重试模型请求”会新建关联任务，保留原问题、补充或最后确认约定，原失败记录和消耗不清空。请求带唯一编号，响应丢失重发返回同一新任务。工具、权限失败不能借按钮冒充模型失败；未知外部调用不能靠自动重发假定零费用。

4.5.19 N19｜上下文超限怎样排查？一定要再用模型压缩吗？

我的回答：不一定。这次两轮补充连同固定协议达六千一百四十字节，超过六千字节输入上限；精简固定说明和 JSON 排版后降至四千九百一十字节，原问题与补充逐项相同，没有额外模型压缩。字节预算是保守上界，不是模型总上下文容量或真实 Token 账单。未发请求的本地拒绝记零模型调用。

4.5.20 N20｜哪些真实故障最体现执行控制层的设计？

我的回答：一是程序生成调查权限，却让模型省略，再把默认空值当作修改约定；我改为服务端固定约定、模型只选动作。二是模型重复填写已继承的应用筛选，程序把等价范围当成不同范围；我只归一完全相同的条件、顺序和重复 IN 值，仍拒绝不同应用、不同操作符及额外条件。修复协议摩擦不能变成放宽授权。

4.5.21 N21｜检查点、操作账本和业务任务分别干什么？

我的回答：检查点告诉流程下次从哪里走，账本记录外部操作是否准备、发送、完成或未知，业务任务与事件负责对外状态。工具回执已确定但图没推进时复用回执。模型调用结果未知时保守停止，不能只根据图节点重新发送。持久化不等于外部供应商恰好执行一次。

4.5.22 N22｜两个 Worker 或迟到结果如何处理？

我的回答：Worker 用租约领取任务，用执行版本作为提交围栏。被接管或取消后，旧执行者即使恢复也不能写回检查点和最终状态。版本围栏保护本地提交资格，不能撤回供应商已经收到的请求。SSE 只是传输，持久事件按序补读，浏览器重连不会重新发起分析。

4.5.23 N23｜用户权限或数据版本在执行中变化怎么办？

我的回答：约定不是永久授权。每轮和读取历史结果都重新检查当前身份、指标依赖及数据绑定，撤权后不能靠旧约定继续查。数据、目录或模型绑定变化时旧任务不能直接按旧条件继续。保存版本是为了追溯和拒绝错误复用，不是自动把任务范围升级到更大权限。

4.5.24 N24｜需要扩大分析范围时怎样获得授权？

我的回答：模型提交完整的新范围及原因，页面展示具体变化，用户明确确认后保存新约定版本。不能用一句含糊的“继续”推定扩大应用、日期或指标权限。新版本不会覆盖旧约定；旧证据是否还能用，要按版本、实际范围和当前权限重新核对。

4.5.25 N25｜怎么评测 Agent，而不只是评测 JSON 格式？

我的回答：分开评测意图与条件解析、工具和计算正确性、调查策略、报告覆盖及费用。冻结问题、数据版本和期望条件，既看最后数字，也看是否遗漏前提、越界、重复调查或不合理停止。模拟响应能验证执行控制和故障反例，真实模型样本才反映接入与策略表现；还应记录失败样本和人工抽样标准。

4.5.26 N26｜一千万发送能证明什么，不能证明什么？

我的回答：它证明当前代码能生成、流式导入并在这份模拟快照上完成指定核对。查询使用经过验证的精确日汇总和授权视图，结果与原始表独立核对。它不等于一千万真实用户，不证明任意明细扫描或并发吞吐，也不把某次 App 列举查询的耗时推广到全部分析。

4.5.27 N27｜状态与结果怎么保存，如何避免塞爆上下文？

我的回答：任务、约定版本、步骤回执和完整受限产物在服务端分别保存。模型上下文只带必要条件、证据索引、整体值和明确裁剪的预览，完整计算读服务端结果。当前单产物仍有大小和组数限制；大规模原始发送记录留在业务表，不一次塞进一行结果 JSON 或模型消息。

4.5.28 N28｜发布和验收如何证明跑的是这版代码？

我的回答：先提交隔离分支、构建带源码版本的候选镜像，核对源码与镜像文件，再用服务器隔离测试库验证。切换前检查任务、备份平台状态和回滚配置，保留数据容器，切换后核对健康、镜像版本、原任务及真实个案。源码、镜像、测试报告和真实结果分别留证，不能把本地测试说成已经云端通过。

4.5.29 N29｜用了 AI 开发，如何说明自己的贡献？

我的回答：我会按真实经历说明本人负责的需求、取舍、评审和验证，不编造手写比例。现场应能解释一次具体失败，提出反例，指出哪层代码会拒绝它，并说明修复为何不扩大权限。调用框架和复制测试数量不足以证明理解；源码证据也不能证明每行代码由谁独立手写。

4.5.30 N30｜下一步优先改什么，为什么不先加多 Agent？

我的回答：优先补真实模型冻结评测、核心问题覆盖判定、有效停止及可观测性，再接入确有数据与工具的新场景。发送标题和正文存在，不等于已证明文案归因；当前目录缺用户消息链路、业务转化等工具时要说明缺口。多 Agent 会增加协调、重复证据和共享预算问题，应先证明单 Agent 的瓶颈，再引入复杂度。

4.6 高风险表述提醒

不声称所有开放问题都能回答、结构合法就符合本意、程序检查能证明因果、一次真实个案等于模型准确率、一千万模拟发送等于生产容量。也不把默认关闭的模型质量评审说成已上线，不把未知费用记零，不把额外数据或多 Agent 的设想写成已实现。

4.7 建议复习顺序

先练一分钟介绍，再画两种执行流程，重点掌握 N04、N05、N07、N08、N11、N16、N19、N20、N25。每题按“用户问题 → 模型决定什么 → 程序检查什么 → 一个失败反例 → 能证明与不能证明什么”展开。数据库和部署细节用于支撑 Agent 的可靠性，不抢走应用设计的主线。
