# 推送结果多轮修改与上下文预算（方案待确认）

## 已确认需求

用户于本次对话确认：自然语言推送查询完成后，可以继续修改查询条件并重查，也可以基于已有结果调整回答。需要保存可回看、可恢复的会话，并处理历史过长的问题。已有“追问处补充条件”的修复继续保留。

## 建议技术方案

1. **会话与版本。** 增加 PostgreSQL 会话、顺序消息及回答版本记录，绑定租户、用户、角色、数据源与指标权限。保存用户消息、可见助手回答、工具请求和结果引用；系统规则与工具定义记录版本，实际模型请求记录有界上下文快照。供应商隐藏推理不是会话记忆。每版回答关联不可变的查询条件和结果，不覆盖旧版本。
2. **修改条件。** 从上一版的完整结构化计划继承，只变更本轮明确要求的内容；生成新任务和回答版本，澄清仍在当前任务内继续。日期、指标、维度、筛选、观察时长变化均重新查询。未知或无法表示的要求进入澄清，不默默丢弃旧条件。
3. **调整回答。** “更简洁/详细、用表格、解释口径”等复用原证据与查询版本，不重新查库。模型选择受限的展示配置，数字、指标口径和数据限制由证据渲染；不允许模型改写业务数值或补造因果结论。先覆盖现有自然语言推送/设备查询，工具分析的执行图与完整报告流程保留。
4. **完整历史与工作上下文分离。** 完整消息落库；模型输入为当前结构化条件、当前展示配置、上一版回答摘要、相关结果引用和最近消息。较早消息逐步移出工作上下文，不从历史删除。涉及被移出内容但无法唯一定位时，澄清所指版本，而不是猜测。
5. **预算。** 发请求前按当前支持的 `byte_bpe_upper_bound` 做保守输入预算校验，并独立保留输出额度；不猜模型有多大上下文。沿用现有 6000 的保守输入上界。先移出旧对话、减少结果预览，最后保留本轮指令、当前完整计划、必要规则和相关证据引用。必要内容仍超限就拒绝发送并明确提示缩小范围/新建会话。可见提示说明历史上下文已收缩；不把裁剪或估算冒充无损压缩/实际用量。完整历史可回看不等于模型每轮都看到全部历史。
6. **恢复与边界。** 请求 UUID + 会话版本防止双击/多标签页覆盖；任务回执、执行租约与数据源绑定继续生效。完成回执可复用，未知模型调用不自动重发。会话上限先与现有订单多轮一致，最多 30 轮；长期个人偏好、跨会话向量检索不属于本次范围。

## 历史收缩的具体规则

- 数据库保存完整用户/可见助手消息及顺序，保存每版完整计划、展示配置、工具参数和结果引用。工作上下文的收缩不删除这些原始记录。
- 必须进入本轮上下文：规则与必要工具协议、本轮指令、当前完整有效计划、当前展示配置、必要证据引用。先计算这些内容的保守预算，超过上界直接提示处理，不先截断再发请求。
- 预算允许时加入最近最多 8 条消息，按时间从最旧开始移出；完整结果仅加入相关汇总和有限预览行，超预算先缩小预览。实际采用哪些消息、引用及是否发生收缩记录在请求快照中，并在界面提示。
- 较早对话不生成反复改写的自然语言滚动摘要；以已验证的当前完整计划作为查询工作状态，避免摘要逐次丢失时间、厂商、筛选和指标。每次被明确替换的旧条件仍在旧版本中保存，不继续当作当前约束。
- 上一版可见回答有完整原文，也有稳定的段落/展示块与证据关联；工作上下文使用必要的回答摘要或相关块。用户明确引用旧消息或版本时按归属校验后取回相关内容，再按相同预算组装。不能唯一定位、已过保留期或片段仍超预算时先澄清/提示，而不是声称记得没有读到的内容。
- 新建会话可从用户确认的当前条件重新开始，不把被移出的旧消息或已失效条件自动当作事实带入。

## 验收

- 原问题 → 澄清 → 结果 → “只看华为/小米” → “改为9月”保留未修改条件，查询结果与独立预期一致。
- “简洁一点/改用表格/解释到达率口径”复用同一证据，SQL 次数不增加，旧回答版本仍可查看。
- 刷新、重新登录、历史选择恢复同一会话及消息顺序；角色、指标撤权和数据源变化后拒绝续接。
- 并发、幂等重试、取消、未知回执、上下文预算边界、长历史缩减与必要条件过长均有真实 PG + 模拟模型验证；不静默截断关键条件。
- 前端实际完成多轮流程与刷新验收，提交 PR，服务器隔离验证通过后统一发布。真实模型调用仍需单独明确授权。
